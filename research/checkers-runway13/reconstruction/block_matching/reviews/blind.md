- **Review scope:** Independent static review of `code_snapshot.md` only, plus the required working agreement and adversarial-review skill. Locations below are line numbers within each extracted source file, not the Markdown snapshot. Input imagery, artifacts, specification, and current run outputs were deliberately not inspected; conditional failures below are not claims that those conditions occurred in the present run.

- **B1 — High: palette indices are treated as brightness in both extraction paths.** `digitize.py:26–39`; `candidates/extract_candidates.py:40–60`. Both readers average `read(1)` and then threshold its numeric values, whereas `register_sheets.py:65–75` explicitly decodes the palette before averaging. For a valid two-entry palette where white is index 1, white becomes `<200` and the candidate path classifies the entire map as ink; the digitizer rejects all seeds. Arbitrary palette ordering also makes averaging indices meaningless. **Repair:** use one shared palette-aware RGB/luminance reader, decode before resampling, and verify binary and reordered-palette fixtures.

- **B2 — High: visual acceptance is not bound to the geometry actually reviewed.** `accept_geometry.py:20–32`. Every input candidate other than `clinic` receives `visually_checked_map_face`; the code does not check an approved `(id, source_id, geometry/source hash)` record or that its referenced overlay exists. A re-extraction with changed threshold/seed, a new epoch, or an additional ID is silently certified using the old visual-inspection statement. **Repair:** apply an explicit reviewed-candidate manifest keyed to immutable geometry/source/overlay hashes; unmatched or changed inputs must remain pending, not inherit acceptance.

- **B3 — High: failed source-registration checks still produce registered outputs.** `register_sheets.py:57,94–96`. `audit_one` reports checksum mismatch, affine disagreement, and invalid core margins, but `main` calls `render(a)` solely because the source ID is selected. Rendering therefore proceeds with the world-file transform even when the audit says it disagrees with the TIFF or the source differs from the receipt. **Repair:** retain the failure report but gate rendering on all required audit and checksum checks; make the run fail or mark outputs explicitly invalid rather than publishing ordinary registered products.

- **B4 — High on regeneration: manual stereo labels are attached to mutable filtered-array offsets.** `aerial_registration/build_sparse_stereo.py:10–11,37–41`. Ground points, roof points, and notes use literal indices into `raw['p1'][raw['fmask']]`, and exported `track_id` is a newly enumerated offset. Changing any earlier inlier membership shifts those offsets and can assign a roof to the ground plane or apply an inspected roof label to another object without error. **Repair:** preserve stable source correspondence IDs, record the inspected pixel coordinates and input-track hash with each manual label, and validate them before solving.

- **B5 — High: rejected stereo points can still establish the metric frame and be reported as roof estimates.** `aerial_registration/build_sparse_stereo.py:19–23,29,50,53`. The four ground-plane points are consumed before checking cheirality, finite coordinates, reprojection error, or plane degeneracy. The subsequent `good` filter gates PLY export only; the report and sensitivity experiment emit the named roof heights unconditionally, including a roof point rejected by that filter. **Repair:** validate every control-plane point before solving, check the ray/plane denominator and similarity-fit rank, and gate named roof estimates on explicit per-variant validity with a reason when unavailable. Do not silently substitute different control points.

- **B6 — Medium: WGS84 geometry carries a contradictory EPSG:2326 property.** `digitize.py:64`; `accept_geometry.py:51`. The digitizer inserts `properties.crs='EPSG:2326'`; the WGS84 export transforms coordinates but reuses the properties unchanged. A consumer following that feature property can interpret degree coordinates as Hong Kong metres. **Repair:** remove the ambiguous feature CRS property from standard GeoJSON, or update it to the output coordinate CRS and preserve original CRS separately as provenance.

- **B7 — Medium: clipping can manufacture a closed region eligible for a strong match.** `candidates/extract_candidates.py:59–67,90–100,125`. Connected components are formed after multiplying by `valid`, so an open white region can be cut into an apparently bounded finite component. Its edge-touching status is calculated but used only in the map-region export, not in best-IoU selection or candidate classification. A modern polygon fully inside coverage can consequently receive a strong score against an artificially clipped component. **Repair:** exclude coverage-edge components from closed-region evidence or propagate an explicit edge-truncated status to every candidate using one; retain them separately for review.

- **B8 — Medium: candidate coverage is reconstructed from a geographic bounding box, not the actual sheet core.** `candidates/extract_candidates.py:58`. Transforming `box(minlon,minlat,maxlon,maxlat)` into EPSG:2326 does not recover the original projected sheet rectangle: projection and taking an axis-aligned envelope do not commute. The resulting mask can include marginal cartography and distort the clipping status at sheet edges, despite the comment promising core-only coverage. **Repair:** use the source index polygon or the independently audited projected core bounds; test points just inside and outside each sheet edge.

- **B9 — Medium: exported region outlines are systematically inset from the component footprint.** `candidates/extract_candidates.py:114–125`. `findContours` returns boundary pixel centres and the code maps those centres into polygon vertices. An `n×m` rectangular component is exported with area `(n−1)(m−1)` pixel areas instead of `nm`; narrow components can collapse and are then dropped even though the eligibility calculation accepted their pixel area. Hole removal is documented, but this exterior half-pixel erosion is separate and unreported. **Repair:** polygonize the binary labels using raster cell edges, as `digitize.extract` already does, then apply the documented hole policy and simplification; test geometry area against pixel-area accounting before simplification.

- **B10 — Medium: world-to-pixel seed lookup uses rounding with an edge-based affine.** `digitize.py:38`. For raster edge coordinates, the containing cell is selected by floor, not round. A seed at column coordinate `10.75` belongs to cell 10 but selects cell 11; the last half of the last cell can be rejected as out of bounds. Near a narrow wall this chooses a different connected region, not merely a harmless subpixel shift. **Repair:** use floor/rasterio's containing-cell index operation and make any preview-pixel-centre-to-world conversion explicit; test half-cell positions and the right/bottom boundaries.
